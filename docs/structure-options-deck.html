The bar every option must clear

What "good" means here

1 · One glance, one answer

Any folder name answers exactly one question — "routes", "a feature", "domain logic" — without reading a doc first. No folder that means two things (today app/ means pages and HTTP handlers).

2 · Flat beats nested

Max 3 levels before you reach code. A path you can say out loud: features/practice/question-card.tsx — not src/app/(student)/_components/practice/__fragments/….

3 · God files can't hide

The structure itself makes 900-line components impossible or embarrassing: every screen has an obvious home for its parts, so parts migrate out naturally.

4 · Docs tell the truth

One AGENTS.md whose layout tree matches reality, one README that never rots. Structure so simple the docs are short.

5 · Cheap to move in

You (and agents) add a screen or a feature by creating files in one obvious place — never touching five directories to ship one feature.

6 · Matches the framework

Next.js owns app/ routing conventions. Winning options work with App Router, not against it — no fighting the toolkit.

Option A · Feature-first recommended

Vertical features — every screen owns its folder

apps/web/ ├── app/ # thin Next routes only │ ├── page.tsx # ← imports features/practice │ ├── parent/page.tsx │ ├── dashboard/page.tsx │ ├── performance/page.tsx │ └── api/… # thin HTTP adapters → server/ ├── features/ # THE unit of organization │ ├── practice/ # student screen: question card, │ │ └── … # feedback, skill picker, grade picker │ ├── assessment/ # test mode │ ├── parent-portal/ # cards, suggestions, export │ └── admin/ # console panels ├── components/ # truly shared: interaction-answer, math-text ├── server/ # shared domain (unchanged) └── test/ e2e/ data/

Why it's good

  • Cohesion: everything about practice — its card, its picker, its state — sits in one folder. The 948-line page dissolves into features/practice/ naturally.
  • Cheap to extend: new screen = new folder. Nothing else moves.
  • Boundary rule is one sentence: features may import server/ and components/; never each other's guts.
  • Still Next-native: app/ stays a thin router — no framework fight.

Who ships this

cal.com/cal.com

Their app is organized as features (packages/features/books, event-types…) with a thin route layer — the most-studied Next.js monorepo on GitHub. Same idea, scaled to their size.

Cost to adopt: medium (split the god page into features — which needs doing under any option).

Option B · Domain packages

Everything reusable is a workspace package

odyssey/ ├── apps/web/ # thin shell: routes + wiring │ ├── app/ components/ test/ e2e/ data/ ├── packages/ │ ├── practice-engine/ # ✅ already exists │ ├── identity/ # accounts, sessions, links │ ├── curriculum/ # catalog + seeder + browse │ ├── learning/ # progression, assessment │ └── ui/ # shared components └── docs/

Why it's good

  • Hard boundaries: cross-domain imports must go through package exports — the compiler enforces architecture.
  • Each domain gets its own tests, README, version — tidy at any scale.

The honest cost, for this repo

  • Every package is ceremony: package.json + tsconfig + vitest + workspace wiring × 5 more.
  • Your own repo rule (inherited from the brief): extract only when two consumers exist. practice-engine earned it; identity/learning have exactly one.
  • More top-level motion, not less.

Who ships this

dubinc/dub · midday-ai/midday · triggerdotdev/trigger.dev

Dub (packages/ui, api, core) and Midday (packages/api, db, ui, engine) are the canonical Turborepo references. Right call for platform teams; heavy for a family-run local app.

Option C · Next-canonical colocation

Framework default, discipline via route groups

apps/web/ ├── app/ │ ├── (student)/ │ │ ├── page.tsx │ │ └── _components/ # private to this route │ ├── (parent)/ _components/ … │ ├── (admin)/ _components/ … │ ├── api/… │ └── layout.tsx ├── components/ # cross-route shared only ├── server/ test/ e2e/ data/

Why it's good

  • Zero invented conventions: route groups (name) and private folders _x are documented Next.js features — every Next dev (and agent) already reads this shape.
  • Colocation law: a screen's parts live beside it; shared-only goes to components/. The god page splits the same way.
  • Cheapest migration of all options — mostly moving files down one level.

The trade-off

app/ still means "pages and API and route-private parts". Feature logic stays smeared between app/(x)/_components and components/ — the thing you dislike doesn't fully die, it just gets politer.

Who ships this

Next.js official docs · create-t3-app · vercel/examples

The default structure of the ecosystem — maximal familiarity, minimal opinion.

Option D · Formal methodology

Feature-Sliced Design — the full ceremony

apps/web/ ├── app/ # layer: routes ├── pages/ # layer: screen composers ├── widgets/ # layer: standalone blocks ├── features/ # layer: user actions ├── entities/ # layer: domain objects ├── shared/ # layer: ui kit, utils └── server/

Why people love it

  • Strict import law between layers — architecture is mechanically enforceable, scales to large teams.
  • Every file has exactly one legal home; nothing is ambiguous.

Why not here — said plainly

  • Six layers for a three-screen local app is process cosplay. You asked for no nested garbage; FSD is professional-grade nesting.
  • Every feature touches 4+ folders; agents need a rulebook to place a file.

Who ships this

feature-sliced.design (methodology)

Widely used in product teams (esp. EU/RU ecosystem) and Next adapters exist. Included for completeness and honesty — not recommended for Odyssey's size.
