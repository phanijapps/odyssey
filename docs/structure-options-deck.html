The naming verdict

You were right — "features" is bookish

Most professional repos

No layer at all.

dub, midday, formbricks, novu, docmost: thin app/ + colocated parts + shared dirs. The route tree is the feature list.

The biggest one

calls it modules/

cal.com — 100k+ stars of Next.js at scale — organizes app logic as apps/web/modules/…. Professional, boring, says what it means.

Nobody serious

uses features/ inside an app

That's tutorial/blog vocabulary (and cal.com's old package experiment). Dropped from every option below.

so

Every option ahead uses either nothing (pure colocation) or modules/ (cal.com's word). Both are industry-proven. Both are two syllables.

Option 1 · The cal.com shape recommended

modules/ + playwright/ + root data/

odyssey/ ├── apps/ │ └── web/ │ ├── app/ # thin routes + api/ adapters │ ├── modules/ # ← cal.com's word │ │ ├── practice/ # sign-in, grade pick, skill browse, │ │ │ # question+feedback, banner │ │ ├── assessment/ │ │ ├── parent/ │ │ └── admin/ │ ├── components/ # cross-screen shared (3 files) │ ├── server/ # domain — unchanged │ ├── lib/ test/ │ ├── playwright/ # e2e — cal.com & dub's home │ └── public/ ├── packages/ │ └── practice-engine/ ├── data/ # runtime state — repo root, │ # actualbudget-style, git-ignored ├── docs/ tools/ README.md AGENTS.md …

Why it's right for you

  • Every complaint answered: e2e → playwright/ (visible, named by tool); data → repo root (one obvious home, like actualbudget); screens → modules/ (professional, kills the god page).
  • Exact match to the most-scaled Next.js repo on earth — you can diff your tree against cal.com's and see the same bones.
  • AGENTS.md structure section: still two sentences.

Proven by

cal.com (modules/, playwright/, server/) · actualbudget (root data/)

Option 2 · The dub shape

No layer at all — pure colocation

odyssey/ ├── apps/ │ └── web/ │ ├── app/ │ │ ├── (student)/ │ │ │ ├── page.tsx │ │ │ └── components/ # screen-private parts │ │ ├── (parent)/ components/ … │ │ ├── (admin)/ components/ … │ │ └── api/… # thin adapters │ ├── components/ # cross-screen only │ ├── server/ # domain — unchanged │ ├── lib/ │ ├── playwright/ │ └── tests/ # unit setup+helpers ├── packages/practice-engine/ ├── data/ # runtime state, repo root └── docs/ …

Why it's good

  • Zero invented vocabulary — no modules, no features; Next's own route groups do the grouping.
  • Smallest diff from today: split the god page into (student)/components/, rename e2e → playwright/, test → tests/, move data to root.
  • Fewest top-level names to remember.

The trade-off

Screen logic lives under app/ — the folder still means "routes and their parts". At 4 screens that's fine; at 15 it starts to smear. dub lives happily this way; cal.com outgrew it.

Proven by

dubinc/dub (this exact shape) · create-t3-app · most Next apps

Option 3 · The twenty shape

E2E as its own workspace package

odyssey/ ├── apps/ │ └── web/ │ ├── app/ (modules/ or colocation — │ │ pick 1 or 2 first) │ ├── components/ server/ lib/ tests/ ├── packages/ │ ├── practice-engine/ │ └── e2e/ # own package.json: │ # playwright dep, runner, │ # specs, fixtures, reporters ├── data/ # runtime state, repo root └── docs/ …

Why teams do it

  • Test deps isolated from the app's bundle — no accidental imports of test code into prod.
  • CI can run e2e as a workspace unit; own reporters, own caching.

The honest trade-off

More ceremony for a 6-test suite: a second package.json, workspace wiring, and the DB-path/env coupling between app and e2e package gets more indirect, not less. twenty earns it with hundreds of specs. Odyssey doesn't.

Proven by

twentyhq/twenty (packages/twenty-e2e-testing)

Sub-decision · where runtime data lives

data/ at the repo root — like actualbudget

odyssey/ ├── apps/ packages/ docs/ … └── data/ # git-ignored; .gitkeep + README ├── odyssey-learning.db # THE file that matters ├── odyssey-curriculum.db # reproducible from seed ├── backups/ # admin one-tap snapshots └── e2e/ # transient playwright DBs

Why root beats apps/web/data

  • Visible at first glance — "where's my data?" has one answer, not a five-folder path.
  • Backup story gets simpler: everything a family must keep is one directory.
  • actualbudget — the most-loved local-first OSS app — does exactly this.

How it stays robust no cwd games

The app resolves the repo root by walking up from cwd to pnpm-workspace.yaml (the monorepo's own marker — the same trick Turborepo uses). Env overrides (ODYSSEY_DB_PATH) still win. Two lines, tested.
