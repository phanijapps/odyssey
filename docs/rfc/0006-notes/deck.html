Odyssey: from platform to product

The full plan to simplify this codebase into a production-ready, three-persona local app on SQLite — and the mockups of where we land.
RFC-0006 · branch simplify/persona-app · commit bcd4e52 · 2026-08-30 · rev 2 (adversarially reviewed)
The goal

One simple app. Three personas. One database.

Everything in this deck serves a single outcome: a local-first child math-practice application a family can actually use — sign in, practice, see progress — with nothing the brief doesn't need.

🎒 Student

Pick a skill → one question at a time, with diagrams, hints and worked solutions. Test mode when ready. One task per screen.

👨‍👩‍👧 Parent

Aggregate progress per child, streaks, what to practice next — and child account management. Aggregates only, never raw answers.

🛠️ Admin

Accounts, the versioned curriculum catalog, question-bank coverage, system health & backup. An operator, not a curriculum pipeline engineer.

Guided by docs/product/briefs/child-math-learning.md (the product goal) and RFC-0003 (persona boundaries). The parent portal moves from “deferred” to in-scope — the owner wants it, and it already works.

The problem you can't see

A fresh clone can't practice math

Found during verification, confirmed by adversarial review: the topic catalog your children browse comes from Gold records in a local SQLite file — and the only writer of those records is the ingestion pipeline. The DBs aren't in git.

fresh clonecode only, no DBs
→
empty cataloggold_curriculum_records = 0
→
no skills to pickbrowse tree empty
→
no practice, no testthe MVP is broken

The fix (Phase 3) new work

  • Enrich the versioned JSON catalog with the fields the browse tree needs (subject, domain, standardCode, standardText…)
  • One-time export of the current 728-record local dataset into that reviewed JSON
  • Idempotent startup seeder: JSON → gold_curriculum_records
  • Seeder ships before ingestion is deleted — the read path never changes

Why it stayed hidden

The ingestion pipeline “worked” locally because a human had already run it against app/odyssey-curriculum.db (728 records, 16 MB). The platform masked its own bootstrap gap. This is the strongest argument that the simple path — a reviewed file in git — is also the safer one.

Phases 2–3 · the big cuts

Memory out. Seeder in. Pipeline gone.

Phase 2 — memory subsystem ~2,000 LOC

  • Deletes server/memory/*, /api/memory, /api/knowledge*, dashboard/graph, 3d-force-graph dep, third DB
  • Strips best-effort projection writes from /api/answer
  • Strips the Knowledge panel from the admin console (kept file)
  • Requires Phase 1: the dead generated-question route imports engram-memory
  • Learning result never depended on projections — by design, provably

Phase 3 — seeder first, then the pipeline ~1,900 LOC

  • Step A (new): enriched reviewed JSON catalog (domain, standardCode, standardText…) + idempotent startup seed into gold_curriculum_records + seeder tests + one-time export of the 728 local records
  • Step B: delete ingestion (promotion, source-importer, curriculum-pi-agent, indexer, routes, ingestion/page.tsx), semantic search (sqlite-vec, embeddings), the ✨ toggle
  • Step C (review finding): kept code imports cut code — remove gold DELETE handler + vector-coupled deletes in gold-query.ts, strip the search route's semantic branch
  • e2e switches its raw-SQL gold seeding to the seeder

Phases 7–8 · production ready on SQLite

SQLite is the right backend — and it's already half-hardened

Already true today verified

✓Native node:sqlite — zero native DB deps
✓WAL journal mode + 5s busy timeout
✓Foreign keys ON, every connection
✓Ordered migrations via user_version, downgrade-refusing (v11)
✓scrypt + per-user salt + timing-safe auth
✓Login throttle, session rotation, 30min/8h expiry
✓Same-origin mutation proofs on every write
✓Atomic question assignment (CAS pool writes)

Added by Phase 8 new work

＋Production admin bootstrap — today none exists (dev fixtures only!); env-gated first-admin seed with zero-admins guard
＋Backup — VACUUM INTO from the admin console (safe under WAL) + cold-copy doc; one file after Phase 7 merge
＋Export & reset — per-child JSON progress export and reset (closes the retention-policy gap)
＋Health probe — schema version, catalog count, generator availability; doubles as the release smoke
＋Config hardening — ODYSSEY_APP_ORIGIN required in prod, absolute DB paths, drop native-extension loading with sqlite-vec
Deployment posture: single-host local-first (family laptop or one small server). SQLite handles this trivially in WAL mode; no server DB or auth service is warranted — that would violate the brief's local-first principle.
